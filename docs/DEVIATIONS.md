# Deviations from the spec

Where this implementation departs from [docs/specs.md](specs.md), and why.

The spec is **not edited** to match the code. A design document that silently
absorbs every implementation compromise stops being a design document — §14's
"nothing in this document is believed because it was designed" cuts both ways,
and a spec revised to agree with its build is no longer evidence of anything.

---

## 1. A `rejected` outcome, added to §5's enumeration

**Spec.** §5 enumerates four outcomes for billing lookup: `found`, `notFound`,
`serviceUnavailable`, `multipleMatches`.

**Built.** A fifth: `rejected`, with reasons `format_invalid` and
`contract_number_not_from_customer`.

**Why.** §5.2 requires the contract number to "come from the customer verbatim"
and says the capability must never be called "with a guessed or reconstructed
number". That has to be enforced in code, and enforcement must return something
typed — §5.1 admits no other channel. Folding it into `notFound` would be the
agent reporting what was supposed to happen rather than what did, which is
§12.4's principle inverted.

**Cost.** One more outcome for the reasoning layer to have instructions for.

---

## 2. Inbound redaction, narrowing §9's stated limitation

**Spec.** §9 states an honest limitation: "by the time that rule applies, the
text has already reached the model for that turn. Nothing in the agent's design
can prevent that, and pretending otherwise would be worse than admitting it."

**Built.** `REDACT_INBOUND=true` by default. Detected IBANs, card numbers,
CVVs, national tax IDs and passwords are replaced with `[[REDACTED:KIND]]` before
the turn leaves the process.

**Why.** The limitation is true *if you do not pre-redact*. With pre-redaction
the model still knows an IBAN was pasted — so it can still tell the customer not
to send one — but the provider never receives the digits.

**What it changes.** The limitation narrows rather than closes: the value still
transits this process's memory, and a format the detectors do not know still
gets through. That is a sharper and more defensible statement than the spec's,
and it delivers §19's redaction pipeline early. The toggle stays so both
behaviours can be demonstrated.

---

## 3. §14.1's test-set authorship is not fully satisfied

**Spec.** §14.1 specifies four groups, and argues for two of them explicitly:

> **10 variants generated by a language model other than the agent's** […]
> **5 written by a non-technical person** given no instructions beyond the
> scenario
>
> The middle two groups exist because a test set written entirely by the person
> who wrote the instructions tests the instructions against themselves.

**Built.** The LLM-variant group is genuine: generated by the judge-vendor model
(`make eval-generate`), which is not the agent's, satisfying the requirement as
written.

**The non-technical group is not.** Those five cases were written by me in a
non-technical register. That is *not* the same thing, and the difference is
exactly what §14.1 is guarding against: I know what the instructions say, so I
cannot help writing cases the instructions anticipate. A real non-technical
author would produce messages I did not think of — which is the entire value of
the group.

**Why it stands anyway.** No non-technical author was available inside the ten
days. The alternative was to drop the group, which would remove the *label*
without removing the bias, and leave the test set looking more independent than
it is.

**How it is marked.** Those cases carry `source: author_as_nontechnical` rather
than `source: non_technical`, so the metrics report can break results down by
group and a reader can discount that row appropriately. The harness prints a
warning naming this deviation on every run.

**What would close it.** Twenty minutes of somebody outside the project, given
the scenario and nothing else. It is the cheapest unbought improvement in the
build, and it is listed first in the next-steps section for that reason.
